# Android UI regression repair

## Investigation before implementation

Compared the working tree against the checked-in Phase 1C checkpoint `cd5fb04`. The recent Android repair lives in the working tree, so the checkpoint is a source comparison. The five reported symptoms were used as acceptance criteria. Device screenshots and touch traces were unavailable in this workspace.

| Regression | Source findings |
| --- | --- |
| Truncated labels | The shared button already allows multiple lines, and the main rows already wrap. Android adds several long, padded actions to those rows without a width bound on the button or its label. The development mode selector also places full-width labels in a horizontal scroll strip with its scrollbar hidden. The exact text measurement behavior requires confirmation on the phone. |
| Map pushed down | The checkpoint put the map first with direct tap-to-add. The current screen puts another title, development launchers, planning modes, endpoint actions, and an expanding search result list above the map. The map then adds a separate camera toolbar. |
| Empty-draft creation | Android removed the planner's map-tap handler and requires a separate placement action and crosshair confirmation. Confirmation is below the map and can be pushed down by search or the keyboard. The straight-line save path still exists and requires two confirmed points. |
| Search confusion | Explore promises places but filters route/workout titles and catalog metadata. Studio search only checks five bundled landmarks and valid coordinates, and appears only after starting placement. |
| Saved routes buried | Saved-route management and the Android Follow Route preview are mounted at the bottom of the editor. Explore's saved-route section sends the user back to the editor for management. |
| Profile diagnostics | The profile editor prints every diagnostic whenever the bundle is in development mode. There is no separate user action to reveal it. |
| Record | The current working tree already moves manual Start above the guide map on narrow screens and permits it during guide lookup. The shared camera buttons also affect Record's map presentation. |

MapTiler documents forward search and autocomplete via keyed requests, with country, bounding-box, and proximity options. The existing basemap key is configured for tiles and styles. Online query transmission and geocoding use need separate authorization, including review of plan quotas, key restrictions, attribution, and storage terms. Once approved, use a provider adapter with cancellation, bounded Kathmandu results, explicit failure states, and documented handling of search text and coordinates. Coverage for New Road would need verification against the authorized service. [Geocoding API](https://docs.maptiler.com/cloud/api/geocoding/) · [MapTiler terms](https://www.maptiler.com/terms/)

The checkpoint already includes a distinct MapTiler place finder on the configured **web Explore map** with disclosure. That entry is independent of Explore's route search and was left in place. The Android Studio search uses local landmark and coordinate data. A coordinate result can be centered and confirmed with a geometry-only map when tiles are unavailable.

## Result and validation scope

| Before | After |
| --- | --- |
| Stacked development controls and long camera button rows | One stack header, Start and Destination actions, a responsive MapLibre viewport, and a small floating camera cluster. Development previews are under Routing tools. |
| Empty Android drafts required discovery of a special placement workflow | Set Start, Set Destination, or tap the map to begin placement. Enter search separately, reposition the crosshair, and confirm. Initial Destination confirmation fits the line. Add, edit, remove, undo, and clear update the draft and its line. Undo also restores a cleared draft. |
| Search results and the keyboard could push the map and confirmation down | Place search opens in a scrollable modal and returns to the same draft and map. Main screen actions use bounded wrapping labels, keyboard dismissal on scroll, and bottom safe-area padding. |
| Explore implied address lookup and pointed saved-route users into the editor | Search routes surfaces matching saved-route titles and route ideas by region, title, or sport. My Saved Routes opens the existing library directly and provides straight-line preview, editing a copy, Follow Route, and sync controls. |
| Development diagnostics loaded above the profile form | Diagnostics require an explicit development-only toggle below the form. Save retains existing validation and reports success in Profile. |
| USB preview calculated as soon as eligible | Calculate route begins the first request. After that, waypoint or travel-mode changes recalculate. Cancel, retry, fallback-free errors, fixture preview, and Back to planning remain available. Only straight-line plans have Save. |

This pass uses JavaScript and TypeScript with the existing Expo SDK 58 modules, MapLibre Native, and route library. Use the installed matching development APK and reload Metro. No new native dependency or APK rebuild is required. Record's Start, GPS, and metrics logic is the existing implementation. Record shares the revised camera buttons and scroll behavior.

## OnePlus 5T physical acceptance

Use the existing Android development APK. In the project directory run `npx.cmd expo start --dev-client` and reload the development client. Start in portrait with default Android Display size and Font size. Repeat the control, keyboard, and map checks with a large system font and larger display size. Test with the phone's navigation bar visible and, where available, gesture navigation. Retain existing app data throughout the run.

1. **Header and labels.** Open **Explore → New route**. Check that Route Studio appears once with Back. Read Set Start, Set Destination, Add waypoint, Undo point, Clear waypoints, and Save route offline in full, including when disabled. Enable TalkBack and confirm camera controls announce Zoom in, Zoom out, Reset map to north, and Fit map to route when available. Check the profile and Record controls at the same font and display settings.
2. **Create a route.** With an empty draft, tap the map near Thamel. Confirm Start. Use Set Destination, open Search for Destination, type `Ratna Park`, select the result, and confirm. Check the S and F pins, automatically fitted orange line, distance, and enabled Save. Add a waypoint. Edit waypoint 2, then undo and verify it moves back. Clear, confirm, and undo again. Check that the ordered line and distance return.
3. **Save and reopen.** Name the draft `OnePlus straight-line check`, save, and wait for feedback. Return to Explore and open **My saved routes**. Open the new plan, then open a previously installed legacy plan. Check the distance and straight-line description. Go offline after Metro has loaded and reopen the local plan. Verify the geometry and pins are shown even if tiles are missing. Edit a copy, save under a distinct name, and verify that both originals still open.
4. **Direct library and scope.** From Explore open My saved routes without entering the planner. With a separate empty test installation, check the no-routes state and its New route action. On a test account with account routes and a local route, check both in the list. Switch to a different test account and verify the previous account's routes disappear and local routes remain. Restore the test account and verify the existing sync status and Retry Sync.
5. **Search scope and empty states.** In Explore search for the saved title, then a catalog term such as `Pokhara`, then an unmatched phrase. Check saved matches, route ideas, and the empty states. In Studio search for `Thamel`, `27.7043, 85.3076`, `91, 85`, and `New Road`. Expect a landmark suggestion, a coordinate suggestion, coordinate validation, and an offline no-match message respectively. Repeat for a waypoint and while offline.
6. **Keyboard and system bars.** Open place search and check that results scroll and select with the keyboard up. Use Back to dismiss the keyboard, then Back to map. Repeat by selecting a result directly. Edit the route name, dismiss the keyboard with Done, Android Back, and dragging the form, and check Save can be reached and pressed. Repeat with Edit Profile. Confirm the tab bar, system bars, and keyboard leave New route, Confirm position, Cancel placement, Save, and Start reachable.
7. **Gestures and camera.** Pan, pinch both directions, and rotate on a warm and a cold map. Repeat with placement active. Press both zoom controls, rotate and reset north, then fit the full line. Use My location during placement and grant permission if prompted. Confirm that the map responds outside the actual floating buttons and that scrolling from outside the map still works. Observe frame pacing and compare with the earlier Metro bundle at the same zoom and connectivity.
8. **Crosshair confirm and cancel.** Tap the map, then pan before confirming. Check that the final pin is at the crosshair. Start editing that pin, move it, and cancel. The previous point and line should remain. Repeat after selecting a search result and verify that selecting alone never writes a waypoint. Quickly cancel after Confirm and check for stale edits if the center read is still pending.
9. **Record and Follow Route.** Open Record directly and choose Walking, Running, or Cycling. Check the timer is idle. Press Start manually, grant precise location, and move outdoors until GPS fixes arrive. Check duration, distance, and moving pace or speed. Pause, resume, and finish. Repeat from a saved route preview using a different sport, away from the route start. Check the teal guide, manual Start above the map on narrow layouts, and the independent GPS track.
10. **USB and fixture.** Follow the existing [loopback runbook](phase-1c3j-live-routing-reliability.md). Keep Valhalla on host loopback. Verify `adb -s <serial> reverse --list` includes `tcp:8002 tcp:8002` and the Metro shell uses `EXPO_PUBLIC_VALHALLA_USB_BASE_URL=http://127.0.0.1:8002`. In Route Studio confirm two Kathmandu points, open **Routing tools → Road-following**, select Walking, and press Calculate route. Verify the road line, duration, and snap information. Switch sport and edit a point. Check that each result matches the draft and Save is absent. Open **Live Kathmandu Routing (USB)** and use the runbook's held request to make Cancel visible. Cancel, retry, and return to planning. Repeat the transport error and retry scenario and open the Kathmandu fixture preview. Verify the original draft survives both previews. With the USB opt-in removed, verify the live entry is absent. Development preview gating is also covered in tests.
11. **Profile.** Sign in with Google and open Profile → Edit Profile. Verify the display name and photo and that developer diagnostics start hidden. Edit Bio and briefly enter invalid data to verify validation disables Save. Reopen a preserved local draft using the existing recovery path. Save a valid draft, verify the Profile saved message, and reopen to verify the data. Open and close Show developer diagnostics in the development bundle. Verify a production configuration does not render the diagnostics control.

Record OS version, font and display sizes, battery-saver state, connection, expected and observed results, and screenshots of any overlap. Automated coverage cannot measure touchscreen geometry, keyboard overlap, GPS reception, or frame pacing. The phone checks remain pending.
