# Phase 1C.3A — Real routing and persistence readiness

Reviewed 21 November 2026. Phase 1C.3B can start with fixtures. MapTiler public release is blocked by the standard beta terms, and saving or syncing provider results requires confirmation of the applicable rights. The repository currently saves straight-line plans. This audit changes documentation only.

## 1. Current architecture and route lifecycle

1. **Draft.** [Route Studio](../src/app/routes.tsx) adds, moves, and removes ordered points via `PlannerMap`. [The planner](../features/routes/planner.ts) turns the user's points into a GeoJSON-shaped LineString in longitude/latitude order and calculates the sum of straight-line segment distances. Opening an edit copies the points into the draft. Saving creates a new ID.
2. **Preview.** The development-only Road-following demo calls [useRoutePreview](../hooks/useRoutePreview.ts), which matches results to the current request and cleans up on focus changes. [The demo](../features/routes/demo-preview.ts) inserts synthetic bends and uses sample speeds. A 250 ms debounce feeds [the routing controller](../features/routes/routing.ts), which snapshots inputs, cancels superseded requests, enforces a default 15 s timeout, and validates geometry, totals, provenance, and ordered waypoint indices. Saving is disabled in demo mode. [The MapTiler adapter](../features/routes/maptiler-routing.ts) is an opt-in factory exercised with injected fetch fixtures. Route Studio is wired to the demo provider. The MapTiler adapter returns `offlineStoragePermitted: false`.
3. **Save and reopen.** Signed-out saves append to the local `routes` value. Signed-in saves queue a private account route locally before sync. Existing device-only routes stay device-only. [SQLite](../services/database.ts) stores JSON in the `kv` table of `stravakinda.db`. [IndexedDB](../services/database.web.ts) uses the `kv` store in the version 1 `stravakinda` database, scoped to the browser origin. [Local writes](../services/planned-routes.ts) serialize operations, use a Web Lock where available, and preserve raw records during successful append/delete. Recovery can expose readable records while warning about invalid ones. The current decoder reconstructs the line and distance from points, and rejects a new planning mode. An incompatible record in the legacy local array can block writes to that array.
4. **Sync.** [Route cloud storage](../services/route-cloud.ts) keeps an account-keyed `account-routes:v1:<user>` cache and queue. SQLite exclusive transactions and IndexedDB read/write transactions apply atomic queue changes. Sync pins the session and compares observed entries before committing changes. [Reconciliation](../features/routes/cloud-sync.ts) validates acknowledgments, preserves conflicts, and uses mutation IDs and revisions. [Supabase](../supabase/migrations/202611160001_planned_route_cloud_sync.sql) enforces owner-only reads, revision-checked RPC writes, and tombstones. [The library hook](../hooks/useRouteLibrary.ts) combines device and current-account routes and masks previous-account results on session change.
5. **Open and follow.** [SavedRouteOpen](../components/SavedRouteOpen.tsx) previews the route in a native modal. On web, Open populates the planner. Follow Route offers walking, running, and cycling and passes a scoped ID and sport to Record via [the guide helper](../features/routes/guide.ts). [Record](../src/app/%28tabs%29/record.tsx) resolves the guide from the local library, excludes deleted or wrong-account routes, and starts recording only through the normal Start action. The workout retains a scoped route reference. Missing guides can be dismissed and recording can continue independently. Planned and recorded lines are separate. Measured distance and pace use workout fixes.
6. **Map rendering.** [Native PlannerMap](../components/PlannerMap.tsx) draws the waypoint line and optional demo overlay. [The Android adapter](../components/maps/NativeMap.android.tsx) translates line and camera calls to MapLibre, with geometry-only rendering available for saved guides. [The non-Android native adapter](../components/maps/NativeMap.tsx) uses react-native-maps. [The web planner](../components/PlannerMap.web.tsx) delegates to [DiscoveryMap](../components/DiscoveryMap.web.tsx), which uses a separate GeoJSON source for the demo. [Native recording](../components/TrackMap.tsx) uses guide points for both the teal line and Start/Finish/intermediate markers. [Web recording](../components/RecorderMap.web.tsx) builds its planned layer from the same points. Every geometry vertex would become a native marker if substituted directly for guide points. Web guide display and offline reload need explicit acceptance coverage.
7. **Transfer and export.** [Activity GPX](../utils/tracking.ts) exports the user's recorded GPS track, including segments, through the activity detail screen. The audited code has no planned-route GPX or GeoJSON file import/export path. Internal GeoJSON rendering and [browser JSON transfer](../scripts/route-import.js) are separate. The latter validates a backup of the original IndexedDB route value and appends additions after an explicit commit. [Backup tooling](../scripts/route-backup.mjs) and recovery must understand future versions before users can rely on them.

Existing tests cover request cancellation and timeouts, demo isolation, injected MapTiler payloads and error handling, local recovery, disk-backed SQLite reopen, native guide navigation/render contracts, cloud lifecycle and atomic queue behavior, and backups. Browser specs cover persistence, transfer, account isolation, conflicts, and tombstones. The Vitest run below does not exercise Playwright, a physical device, or provider coverage. Physical Android visibility of the demo remains unverified.

## 3. Unconfirmed requirements and blockers

- Obtain written provider answers on access, public release, approved request architecture, plan/billing and limits, attribution, retention, offline saves, private cloud sync, and user exports. Record permissions per capability. The adapter's current boolean can express only a fraction of that policy.
- Build a Nepal evaluation matrix for the authorized pilot. Include Kathmandu Valley alleys and pedestrian paths, Pokhara mixed roads, rural links, stairs, bridges, restricted roads, and isolated trailheads. Check both pedestrian activities and cycling, with two-point and multi-stop cases. Compare snaps, route continuity, access and surface against known local conditions. Define acceptable snap distances and failure thresholds before expanding the pilot. A missing path can cause a detour or no route, and a mapped road can still be unsuitable.
- Confirm request limits and collect authorized sanitized response fixtures covering snapped points, round trips, repeated waypoints, adjacent-leg junctions, unavailable routes, malformed data, and throttling. Pin fixtures to the documented API revision. Existing mocked fixtures verify the current assumptions rather than the deployed beta.
- Web offline recovery depends on the app shell already being available, the same origin, and retained browser storage. Test shell availability independently from IndexedDB durability. Android physical-device rendering requires a field check. GPS distance/pace troubleshooting and map optimization are explicitly out of scope.

## 4. Real routing persistence proposal

Use a strict versioned union. Decode existing straight-line records as version 1, regenerating the established straight-line representation from valid legacy points and retaining unknown creation dates as null. Add a version 2 record for provider routes. The current `SavedRoutedPlan` is a preview-era proposal and is unsupported by today's loaders.

| Element | Version 2 provider route |
| --- | --- |
| Identity | Stable route ID, title, kind, schema version, planning mode, createdAt, updatedAt. Ownership remains in the repository/sync envelope. |
| User intent | Ordered raw `waypoints` and app activity profile. Preserve user-selected coordinates even when the provider snaps elsewhere. Derive the straight-line preview from them. |
| Geometry | One canonical WGS84 GeoJSON LineString using longitude/latitude pairs, with a geometry version and ordered waypoint-to-vertex indices. Preserve optional snapped coordinates if validated and permitted. Raw waypoint markers remain visibly distinct from any snapped locations. |
| Estimate | Provider distance in meters, optional estimated duration in seconds, and the actual profile/options used. Replacing the geometry replaces its estimates and waypoint indices atomically. |
| Provenance | Allowlisted provider, provider profile and API revision, calculation time, sanitized attribution, and optional non-sensitive response ID. Keep geometry revision separate from the Supabase sync revision. |
| Demo | In-memory preview result with its synthetic provider identity. Save and sync reject demo shapes, including records submitted outside Route Studio. Imports cannot promote demo or arbitrary geometry to trusted provider provenance. |

Use a shared decoder for open, save, queue, remote hydration, conflict resolution, and backup/import. Validate supported schema and provider/profile pairs, ordered waypoint mappings, finite coordinate ranges, nondegenerate geometry, length, duration, dates, and payload bytes before a transaction. Validate provider provenance at the trusted adapter/backend boundary. If integrity against modified clients is required, use an approved server-issued receipt binding geometry, waypoints and metadata, verified at account writes. A client-supplied provider name or offline permission flag alone cannot prove provenance. Check permissions separately for local save, cloud sync, export, and retention.

Keep storage precision from the normalized provider result initially. Enforce separate waypoint, vertex, response-body and saved-byte caps. The current preview cap of 100,000 vertices is a defensive ceiling and can exceed practical device or storage budgets. The current cloud contract caps a plan at 4,000,000 bytes in SQL while the JS check counts characters. Align the limits in actual bytes for the new format, with headroom for queue conflicts, transport and parsing. If display simplification is later required, measure its error and retain waypoint anchors and canonical geometry.

Use a shared guide presentation selector for saved preview, Android and web. Draw and fit to canonical geometry and place markers from ordered waypoints. Handle loop endpoints, style readiness and foreground recovery. Prevent guide updates from stealing the camera while GPS follow is active. A guide loaded offline comes from stored geometry with no recalculation and may appear over a blank basemap. Store the scoped reference as today and pin the resolved version in the recording session. If that version is replaced or removed on restart, show the guide as unavailable until explicitly reselected. Avoid copying provider geometry into workouts. A lost guide leaves the workout usable and has no effect on measurement.

## 5. Backward compatibility and migration plan

- **SQLite and IndexedDB — no physical schema migration required.** Existing KV containers can hold versioned records. Keep version 2 device rows and account queues under versioned keys so older binaries can still write their legacy libraries. Reuse atomic KV updates. Keep device routes local, keep account caches partitioned by user, and never mirror a routed record into the old library as a straight-line version with the same ID. Unsupported future rows must be preserved and isolated without blocking compatible rows.
- **Supabase — a migration is required before syncing provider routes.** The checked-in `valid_planned_route` and client `validateCloudPlan` require straight-line geometry to match waypoint coordinates exactly. JSONB has capacity for the new shape, but widening the existing table's check alone could let older clients encounter unsupported rows during a library fetch. Prefer an additive routed table and versioned write RPC with owner RLS and the established revision, mutation, and tombstone protocol. Existing endpoints keep the current contract and older clients keep using them. Preserve old rows in place. No backfill is needed. Verify policies and RPC constraints in a disposable environment before rollout.
- **Conflict and deletion.** Queue complete route snapshots and compare the expected revision and mutation ID. Preserve a losing edit intact for explicit cloud-version selection or Save as Copy with a new ID. A tombstoned ID cannot be resurrected by stale retries, restores, or another tab. Current tombstones retain a plan payload. Confirm provider retention and user deletion requirements before choosing routed tombstone storage, and retain only the minimum allowed identifiers and revision data after any permitted purge.
- **Account switching.** Pin user/session through request, save and sync, cancel in-flight previews on account changes, and mask old-account results immediately. Serialize changes so a late sync result cannot overwrite a newer edit/delete. Clear or retain private caches according to approved retention policy, with account visibility enforced independently of connectivity.
- **Backup and export.** Update backup readers and restore tools to preserve complete supported versions, provenance, and attribution. Provide a dry-run and explicit add-only restore. Unknown or conflicting records should be reported without destructive rewriting. If file exports are approved, GeoJSON can carry the canonical line with metadata and separate waypoint features. GPX can carry the line as a planned track and original points as waypoints, with metadata/attribution in supported fields or a companion file. Warn about full coordinates before explicit export. File imports require a bounded parser, an imported provenance class, and no automatic sync or trust of embedded provider claims. Preserve the existing recorded-GPX path independently.

## 6. Security and cost considerations

- Prefer an authenticated, bounded server-side exchange **after provider approval**. Keep a dedicated entitled credential in server secret storage. A public Expo/web build cannot keep a client credential secret, and origin or User-Agent restrictions are exposure controls. Use the existing map credentials only for their configured purpose. Redact URLs, keys, route coordinates and raw response bodies from logs and telemetry. Render attribution as validated text and safe links, since the provider example includes HTML. Minimize and disclose waypoint data sent to the provider.
- Limit calls to an explicit Calculate/Retry action, deduplicate equivalent in-flight requests, and bind a response to the current draft and account. Apply server and client deadlines. Clear stale results on edit, profile change, blur, and account switch. Abort promptly and assume a dispatched cancellation may still consume quota. Disallow saving a result for a prior request.
- Budget with per-user and global limits, an account spend cap if supported, alerts, and a default-off kill switch. Track request count and status without location payloads. As a planning illustration, 10,000 routes would consume 80,000 request units under the published calculator. Confirm account-specific charges before using that estimate. Handle offline, timeout, invalid data, access denial, no-route, 429, and server errors explicitly. Honor bounded Retry-After when available. Keep the editable straight-line plan and require an explicit straight-line save after a routing failure. ## 7. Recommended implementation steps

1. Seek written provider confirmation and define pilot limits, retention, and approval gates. Use local fixtures while decisions are pending.
2. Add the versioned record decoder, provenance checks and scoped repository operations. Exercise rollback, partial writes, unknown versions and quota errors on both platforms. Update backup/restore before exposing new saves.
3. Wire fixture-generated routed geometry through Route Studio, saved preview and Follow Route. Verify marker counts, camera behavior, offline states and profile labels on Android hardware and browsers.
4. Stage the additive cloud contract only after cloud rights are confirmed. Test session swaps, old clients, races, deletion, conflicts and round-trip geometry on disposable Supabase. Keep writes gated during staged rollout.
5. With separate authorization, run a limited internal Nepal pilot with an entitled credential. Review routing quality, attribution, cost and error telemetry before opening a production gate. If the provider cannot meet release or persistence requirements, retain straight-line planning and evaluate a provider with suitable terms.

## 8. Phase 1C.3B acceptance criteria

- [ ] Default builds make zero live Directions calls. Documented approval and a controlled pilot flag are required for provider traffic. Public rollout, local caching/saving, private cloud sync and exports each honor their own confirmed permissions.
- [ ] Walking and running use the approved pedestrian mapping, cycling uses the approved bicycle mapping, and an ordered multi-waypoint result is drawn from actual provider-shaped fixture geometry. Units and estimates are correct and the UI labels the selected mode.
- [ ] Fixture tests cover stale/cancelled requests, account switch, duplicate calculation, offline, timeout, denied entitlement, rate limits, no route, malformed/discontinuous geometry and oversized responses. Demo output cannot pass the save, cloud, backup import, or provider provenance boundaries.
- [ ] A legitimately saved route reopens after restart from SQLite and IndexedDB, with identical canonical geometry, provenance and estimates and zero Directions calls. Test offline Android and web with an available shell, plus a clear web state when shell or storage is unavailable.
- [ ] Route Studio, saved preview and Follow Route render the canonical line. Start, Finish and intermediate pins match user waypoints, guide fit includes off-waypoint bends, and the measured GPS track remains visually and numerically independent. Check physical Android, supported browsers and the non-Android native path.
- [ ] Legacy data opens, saves, syncs and deletes as before. Old clients never receive unsupported routed rows. Authorized routed cloud sync preserves exact geometry, conflicts, ownership, deletion and retry idempotency. Unsupported or corrupt records are recoverable without erasing valid records.
- [ ] Backup/restore preserves supported versions, ownership and attribution. Any approved export preserves its geometry and attribution, leaves legacy activity GPX intact, and excludes hidden, deleted and wrong-account routes.
- [ ] Before any live expansion, authorized Nepal field samples meet the agreed coverage, snapping and continuity thresholds, and limits prevent calls after the spend/usage threshold.
