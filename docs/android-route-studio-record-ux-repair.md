# Android Route Studio and Record UX repair

## Root causes from the code audit

| Report | Confirmed cause and limits of the evidence |
| --- | --- |
| Android map feels slow | Planner fits twice at readiness and refits on every road preview object change, including while adding pins. Record can refit the guide at readiness and again from its effect. Unguided GPS follow recenters and resets zoom on accepted positions. Map style loading already caches by URL and camera state is not driven by continuous React updates. The relative contribution of native tile rendering and GPU load on the OnePlus requires device measurement. |
| Pinch zoom | Native pinch is enabled by default. App camera commands can interrupt exploration. The map is inside a vertically scrolling page, and the installed MapLibre Android implementation already requests parent touch interception be disabled during map gestures. Gesture failure frequency requires reproduction. |
| Rotation and north-up | Native rotation is enabled by default with the small native compass. Planner and Record lack explicit zoom and reset commands. GPS recentering previously applied a fixed zoom. |
| Place search | Planner has no geocoder wiring or coordinate entry. The existing Android MapTiler key is configured for map tiles and style. |
| Waypoint precision | Map taps append immediately. Moving an existing point is available only in the synthetic demo. There is no confirm step or center read. |
| Normal planning straight lines | Route Studio saves with `createPlan`, which joins ordered waypoints directly and derives straight-line distance. The synthetic demo and the isolated USB adapter are separate preview paths. |
| Saved guide straight lines | The local decoder reconstructs legacy geometry from points. The cloud contract requires these coordinates to match the points. Follow Route passes a scoped ID and sport, and Record reconstructs a guide from those saved points. Changing sport does not run routing. |
| Record Start | Resolved guides open Record in Map view, putting Start below the map on a narrow viewport. A pending guide lookup also explicitly disables the control. The native recorder checks permission and existing activity state without reading guide geometry or checking proximity. A touch interception failure specific to this phone has not been reproduced. |
| Cancel visibility | Phase 1C.3J already puts Cancel in the Calculate/Retry slot while loading and aborts through the shared controller. Fast responses can skip a visible loading frame. |

## What changed

- On narrow Android screens, Record puts the accessible Start, Pause, Resume and Finish controls above the guide map. The text label is inside the Start target. Guide loading no longer disables the control. A scoped guide reference can resolve after Start, and a known missing guide allows recording without one. Location permission and initialization errors are shown above the controls. The recorder still checks the existing prerequisites and measures only accepted GPS fixes.
- The Android map enables pan, pinch zoom and rotation and disables pitch in the embedded map. Zoom and Reset north change only the named camera property. Route fitting uses the route line, runs once on initial display, and can be requested explicitly. Planner pins no longer trigger a fit when changing an unfinished preview. Android GPS follow is opt-in and preserves zoom and bearing. A manual map gesture disengages follow. My location requests foreground permission on demand or uses the latest accepted recording position. The Record map skips elapsed-time-only renders. Native guide diagnostics limit retries and stop querying once verified. Basemap styles still use the existing cache and texture view.
- Android Route Studio has Set/Edit start, Set/Edit finish and Add/Edit waypoint actions. Add waypoint inserts immediately before Finish. Select a search result or pan to center the crosshair, then explicitly confirm. Cancel leaves the draft intact. The map no longer adds points on tap in the ordinary Android planner. Saved-route and Record guide lines use the stored line exposed by the current loader, with independent waypoint markers. The supported legacy loader supplies a straight-line line string.
- In Android development Route Studio, Road-following uses the same draft, selected travel profile, Valhalla adapter and exact USB origin as the separate live preview. Confirming an edit or changing travel mode replaces the pending calculation. Without the approved endpoint, the preview shows an unavailable message. Transport and validation errors leave requested pins visible and offer Retry. The preview displays only genuine decoded Valhalla lines and exposes no save action. Straight-line mode remains the explicit legacy save path. The synthetic and Kathmandu fixture previews remain available.

## Search provider decision

MapTiler documents place and address search, autocomplete, geographic constraints and key-authenticated requests. The current Android key is wired to tile and style requests and does not establish approval for geocoding or its quotas. MapTiler meters autocomplete calls as requests or as geocoding sessions depending on integration, with separate session quotas. The project's account tier, remaining budget, key restrictions and Nepal address coverage were not verified. No external geocoding requests are made. [Geocoding API](https://docs.maptiler.com/cloud/api/geocoding/) · [Usage and quotas](https://docs.maptiler.com/guides/account/sessions-vs-requests/) · [Pricing](https://www.maptiler.com/cloud/pricing/)

The fallback searches an offline shortlist and accepts latitude, longitude. Lookups debounce for 200 ms and cancel the timer on edits or exit. The UI displays lookup and no-match feedback. Search text stays in the component, and selecting a result only moves the map. Landmark coordinates are approximate starting points and require confirmation. [Thamel coordinates](https://en.wikipedia.org/wiki/Thamel) · [Ratna Park coordinates](https://www.geonames.org/10276875/ratna-park.html) · [Pilot landmark points](phase-1c3-kathmandu-pilot.md#phase-1c3f-local-routing-validation)

## OnePlus 5T acceptance checklist

Use the existing Android development client with MapLibre Native and reload the Metro bundle. All changes use JavaScript and existing native APIs. A new APK is unnecessary for a matching client. Keep a working basemap for gesture evaluation, and repeat a saved guide check without tiles. The OnePlus was unavailable in this workspace and these checks are pending.

1. In **Explore → + beside Discover routes → Route Studio → Saved routes**, open a saved route away from its first waypoint. Choose **Walking** under Follow Route. Confirm Record opens with a teal straight-line guide and **Start** above the map. Verify the timer remains idle until you press Start. Press the icon or its text label. Grant precise location and wait for a fix outdoors. Walk far from the guide start, pause, resume, then Finish. Verify orange GPS points start at your actual position, distance and pace reflect movement, and the saved activity does not acquire the guide line. Repeat the handoff with Running and Cycling and verify the selected sport.
2. Deny location access on a fresh manual Start. Verify the permission error by the controls and that a workout did not start. Restore access, then test with location services disabled. Verify clear guidance and retry once enabled. Start with a guide and reopen Record after an interruption to check ordinary recovery.
3. In planner and Record maps, pan with one finger, pinch in/out, rotate with two fingers, then use **Zoom +**, **Zoom −**, **Reset north**, **Fit route** and **My location** where applicable. Verify north reset keeps the current center and zoom, Fit includes the route shape, and GPS does not reset the camera while exploring. In Record, explicitly enable Follow location, pan to turn it off, and wait for a new fix. Scroll the page from outside the map. Compare responsiveness before and after with the same tiles and zoom. Test cold and warm tile loads.
4. In Android Route Studio choose **Set start**. Search for Thamel or enter `27.7043, 85.3076`. Tap the result and confirm the map centers there without adding a waypoint. Pan or zoom and tap **Confirm position**. Set Finish, search for Ratna Park or use `27.7125, 85.3139`, and confirm. Add an intermediate waypoint and check it appears before Finish. Edit an existing point and cancel, then edit and confirm. Pan elsewhere with placement closed and verify no extra pins appear. Search for an unknown address and an out-of-range coordinate and verify the no-match message.
5. With the exact opt-in and approved local pilot already running, check **adb reverse --list** and host API status using the [USB runbook](phase-1c3j-live-routing-reliability.md). In ordinary Route Studio select **Road-following**, confirm two or more points, and switch Walking, Running and Cycling. Expect road geometry, totals and distinct snap warnings for the matching draft. Change a waypoint and confirm the prior line is cleared while recalculating. Interrupt USB forwarding, verify Retry and no straight fallback, then restore forwarding and retry. In a development bundle without the opt-in, expect the explicit unavailable state. A production bundle uses the straight-line planner.
6. Open **Live Kathmandu Routing (USB)** and verify Cancel is in the Calculate/Retry position during a held request. Use the [local held-connection procedure](phase-1c3j-live-routing-reliability.md#hold-a-request-for-physical-cancellation-testing) in a separately authorized device session. Tap Cancel, verify the same preview pins and no result or late error, retry, and use Back to planning to verify the original draft. Repeat in the ordinary planner if its request remains pending. Warm Valhalla may finish before Cancel is visible.
7. Leave road-following, switch explicitly to **Straight-line**, and save a new copy. Reopen it and verify legacy straight-line geometry, offline loading, and the usual sync behavior for account routes. Verify the Kathmandu fixture preview still loads and saved routes already on the device open unchanged.

Known device limits include tile and GPU load on the older phone, the embedded viewport inside a scrolling page, and GPS acquisition under weak signals. Only the pinned pilot graph is available for USB routing. Running uses pedestrian geometry and walking-pace estimates. The automated tests exercise camera configuration and commands, and the phone checklist is needed to characterize touch handling, responsiveness and frame pacing.

## Road-following persistence remains a separate phase

1. Approve local save, account sync, export, retention and OSM/Valhalla attribution and data-use terms. Keep the current development preview ephemeral until that approval and an independently approved routable production provider are in place.
2. Add an explicit versioned route record with separate requested WGS84 waypoints and canonical GeoJSON LineString in longitude/latitude order. Store ordered waypoint-to-vertex indices, optional snap positions and warnings, provider totals, app and provider costing profiles, provider/API/graph revision, calculation time and validated attribution. Atomically replace geometry and metadata. Reject fixtures, demos and untrusted provenance at a trusted write boundary.
3. Keep existing SQLite and IndexedDB physical schemas if the existing KV containers suffice. Add separate versioned keys and atomic repositories for device routes and account queues. Leave legacy rows in place. Older clients must continue to read and write only legacy keys. Apply byte and vertex bounds and test corruption, failed writes, restarts, backup/restore and offline preview.
4. After cloud approval, add an isolated Supabase contract for the versioned format with owner RLS, validated payload limits, a versioned write RPC, idempotent mutation identifiers, optimistic revision checks and tombstones. Keep current endpoints and validators for legacy data. Keep losing edits available for explicit resolution or Save as Copy and prevent late writes or stale restores from resurrecting a deleted route.
5. Drive all saved previews and Follow Route maps from one validated presentation model. Render and fit the canonical line and place markers from requested waypoints. Record keeps a scoped reference pinned to the selected revision, and its GPS track and statistics remain independent. Validate Android and web parity, account switching and missing revision behavior before enabling saves. [Detailed persistence readiness audit](phase-1c3-routing-readiness.md)
