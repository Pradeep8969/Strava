# Phase 1C.3B — Production routing provider evaluation

Reviewed 21 November 2026 against official documentation and published terms, following the [Phase 1C.3A readiness audit](phase-1c3-routing-readiness.md).

**Primary recommendation: self-host Valhalla for Nepal**, subject to a coverage benchmark, data-license review, and a funded operating plan. It keeps sensitive waypoints within infrastructure StravaKinda controls, lets the app pin and roll back its routing graph, and avoids dependence on hosted API terms for ordinary route retention. The OpenStreetMap data license and any additional data-source terms still apply. Keep straight-line planning as the immediate fallback. Use hosted OpenRouteService as a managed fallback only after the privacy, output licensing, and quota gates below are satisfied. This is a provider selection for implementation planning. Production readiness and actual Nepal route quality are unverified.

**Status labels.** VERIFIED means an official source establishes the stated capability or published condition. UNCONFIRMED means the production plan, rights, data quality, or operational performance still needs evidence. BLOCKED identifies a production gate under current terms or missing approval. Plan prices and rate limits below are published figures, not project entitlements or quotes.

## 2. Commercial, security and operational comparison

### MapTiler Directions with explicit production authorization

- **VERIFIED — published billing model.** The Cloud calculator lists eight request units per route. General allowances are 100,000/month Free and 500,000/month Flex, with custom limits on Custom. Published Flex API-request overage is USD 0.15 per 1,000 request units. The beta page describes a future logistics-session model. **UNCONFIRMED** — Which plan, quota, overage, rate limits and SLA apply to this app's Directions traffic. [Cloud pricing](https://www.maptiler.com/cloud/pricing/) · [Routing beta](https://www.maptiler.com/routing/)
- **BLOCKED — public production under standard beta terms.** Written production authorization must cover a public mobile/web fitness app and its expected usage. Cloud terms require approval for proxying. The current map key establishes zero Directions entitlement. Require an approved dedicated server credential or a provider-approved alternative and confirm the account's specific access. [Cloud terms](https://www.maptiler.com/terms/cloud/) · [API key guidance](https://docs.maptiler.com/guides/developer/credentials/api-key/)
- **VERIFIED — temporary personal caching and outside-service use of Routing results are addressed in the Cloud terms.** **UNCONFIRMED** — Durable device retention, account sync, app-user export, and rights after termination for this specific service. Keep those capabilities blocked until written confirmation. Carry the provider-returned attribution and OSM credit where applicable, including in databases created from search results. [Cloud terms §§5–6](https://www.maptiler.com/terms/cloud/) · [General terms §6](https://www.maptiler.com/terms/)
- **Operations.** Low graph maintenance. High dependency on beta availability and the negotiated commercial terms. Standard beta terms provide no SLA and permit suspension. Use as an alternative only if written approval closes these gaps. [Cloud terms §4.2](https://www.maptiler.com/terms/cloud/)

HeiGIT staff confirmed Standard allows commercial use. **UNCONFIRMED** — Higher-volume commercial pricing, SLA, organization account ownership, and any negotiated limit. ### Self-hosted Valhalla

- **VERIFIED — MIT engine and regional container deployment.** No provider API key, per-route vendor fee, or hosted free-tier quota applies to the engine. The app still needs an authenticated first-party gateway, request budgets and limits. Other self-hostable engines include ORS and GraphHopper. Prioritize Valhalla because it offers pedestrian and bicycle costing, regional graph builds, and a managed Valhalla comparison using a similar route contract. [Valhalla project](https://valhalla.github.io/valhalla/) · [Container documentation](https://github.com/valhalla/valhalla/blob/master/docker/README.md) · [ORS project](https://github.com/GIScience/openrouteservice) · [GraphHopper project](https://github.com/graphhopper/graphhopper)
- **VERIFIED — ODbL applies to OSM inputs.** Self-hosting removes a hosted API contract from the decision. Assess individual route outputs, aggregated route storage and public bulk distribution separately under ODbL. A stored personal route and a corpus capable of reconstructing substantial source data raise different obligations. Confirm whether any graph or accumulated output is a Derivative Database and what offer or share-alike obligations apply when publicly used. Keep an input license inventory and apply OSM attribution in route views and distributed artifacts. Apply additional source notices if elevation or auxiliary datasets are introduced. **UNCONFIRMED** — Final license treatment of the intended corpus and export flow. Keep bulk geometry exports out of the initial release. [Valhalla data sources](https://valhalla.github.io/valhalla/contributing/data/data-sources/) · [OSM attribution](https://osmfoundation.org/wiki/Licence/Attribution_Guidelines) · [OSMF Produced Work guidance](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Produced_Work_-_Guideline)
- **UNCONFIRMED — real operating cost and reliability.** Budget serving replicas, a separate graph-build job, graph artifact and rollback storage, data transfer, observability and on-call time. A Nepal PBF of roughly 396 MB gives an input-size reference only. Benchmark peak build RAM, disk, wall time, serving memory and latency before selecting instances or projecting monthly cost. Compare a single-instance pilot with a two-replica production service. Include patching, failed builds, monitoring, incident recovery and data refresh in the monthly estimate. [Nepal extract](https://download.geofabrik.de/asia/nepal/) · [Valhalla container build knobs](https://github.com/valhalla/valhalla/blob/master/docker/README.md)

StravaKinda owns availability, incident handling and capacity. Validate near-border graph continuity and use a justified buffered extract if the Nepal boundary clips legitimate routes. Avoid exposing graph tiles or raw OSM extraction endpoints.

## 3. Offline viewing and fallback behavior

All five options can yield line geometry for Android and web. **VERIFIED from Phase 1C.3A** — the existing storage and map architecture can display a locally available guide. **UNCONFIRMED** — routed records on physical Android and the supported web offline shell. Offline viewing uses saved geometry, needs no Directions call and does not imply an offline basemap or on-device route calculation. Basemap licensing and availability remain separate. Each hosted result is eligible for offline replay only within documented or agreed retention rights.

During a failure, keep the draft and existing saves available. Offer an explicit retry or straight-line planning. Preserve saved geometry, its original provenance, and user-selected waypoints. A fallback provider is an explicit request for a **new preview**, with independent cost and data-disclosure controls. Avoid silent provider failover, automatic fan-out and relabeling stored geometry. If no hosted fallback clears the permission gates, use straight-line mode until the primary service returns.

## 4. Exact requirements before implementation and release

1. **Approve the operating and licensing model.** Identify the owner for the Valhalla service, graph pipeline and incident response. Record approved inputs, ODbL treatment for saved routes and aggregated data, and attribution text and placement. For any hosted use, obtain current applicable terms covering public Android/web traffic, auth and gateway use, privacy and waypoint handling, per-user and global limits, fees/overage, data retention and region, durable device storage, private Supabase sync, offline replay after termination, attribution and GPX/GeoJSON export. Track each capability as a separate release gate. Obtain approval before creating accounts, enabling billing, or using live endpoints.
2. **Verify Nepal fitness routes.** Use an agreed corpus covering Kathmandu Valley alleys, stairs, pedestrian areas and access restrictions, Pokhara cycling and mixed-surface routes, rural road connections, bridges, trailheads, disconnected paths and extract borders. Include walking, running and cycling, two-point and multi-waypoint requests, loops and known no-route cases. Suggested pilot gate is at least 30 labeled positive and 10 negative cases, at least 95% acceptable positive routes, and zero known forbidden or disconnected paths misrepresented as successful. Agree on snap tolerances by context with local reviewers and record field evidence. These are proposed targets, not measured results.
3. **Build a reproducible primary service.** Pin Valhalla image digest, the dataset date/checksum, graph options and costing defaults. Build outside the request-serving replicas. Smoke-test every candidate graph, publish immutable artifacts, use health/readiness checks, and retain a last-known-good graph for rollback. Start with a weekly refresh target and review field feedback. Load-test peak traffic, graph replacement and a replica outage. Set latency, uptime and spend targets from measured demand before public rollout. Document loss of service, graph-age alerts and recovery ownership.
4. **Introduce the first-party API using fixtures first.** Keep the existing adapter available and default live routing off. Authenticate requests, scope them to the current account or an explicitly budgeted guest session, reject arbitrary upstream URLs, and rate-limit by user and globally. Set explicit waypoint, distance, response-byte and geometry-vertex caps. Normalize each result into WGS84 longitude/latitude geometry, meters, seconds, ordered waypoint mapping, app profile, provider profile, source/version, and sanitized attribution. Key results to draft and session. Use cancellation, deadlines and bounded retries. Distinguish invalid input, no route, timeout, offline, quota and provider errors. Exclude location and secrets from telemetry and set an application budget cutoff. Use a private engine network or approved backend authentication. Avoid shipping upstream keys in Expo or the browser.
5. **Implement versioned persistence after approval.** Add a strict versioned record in the existing SQLite/IndexedDB KV layer and an additive, owner-isolated Supabase schema/RPC for routed records. Follow the Phase 1C.3A migration plan. Preserve original waypoints, geometry, route estimates, attribution, update times and geometry version together and keep existing rows and older clients compatible. Validate demo rejection, account switching, conflict copies, idempotency, tombstones, deletion and backups through both normal and direct write paths. Gate offline saves, sync and export independently, including for fallback results. Confirm exact geometry on reopen and render Follow Route from that stored line. Keep the planned distance and recorded GPS measurements independent.
6. **Release by evidence.** Exercise fixture integration and storage tests, a disposable cloud contract, Android physical-device and browser offline reopen, legacy and current client compatibility, authorization and budget limits, and a documented rollback. Review licenses, Nepal coverage, operational cost and reliability together before authorizing a pilot or production traffic. A failed gate keeps the affected capability disabled.

This phase used documentation only. No Directions requests, credentials, billing changes, app changes or database migrations were made.
